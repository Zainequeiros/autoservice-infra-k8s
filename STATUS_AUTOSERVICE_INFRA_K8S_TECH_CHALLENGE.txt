3) O QUE JÁ FOI FEITO (E POR QUE)

3.1 Estrutura e governança de IaC
- Feito:
  - Módulos Terraform: `network`, `eks`, `gateway`, `observability`.
  - Ambientes segregados: `terraform/environments/homolog` e `terraform/environments/prod`.
- Por quê:
  - Reuso, clareza de responsabilidade e evolução por domínio.
  - Redução de risco de drift entre ambientes.

3.2 Rede e cluster Kubernetes
- Feito:
  - VPC com subnets públicas/privadas e NAT.
  - EKS com managed node groups e parâmetros de escala por ambiente.
  - Add-ons base do cluster.
- Por quê:
  - Atender escalabilidade e alta disponibilidade com menor overhead operacional.

3.3 API Gateway/Ingress
- Feito:
  - Traefik via Helm com exposição por Load Balancer.
  - IngressClass explícita para integração com a aplicação.
  - Metrics Server para HPA.
- Por quê:
  - Atender requisito de gateway para roteamento e entrada das APIs.

3.4 Hardening de segurança (evolução aplicada)
- Feito:
  - `cluster_endpoint_public_access = false` por padrão (homolog/prod).
  - Validação para bloquear `0.0.0.0/0` quando endpoint público for ativado.
  - `is_default_ingress_class = false` por padrão.
  - Suporte a HTTPS no gateway via ACM (`gateway_acm_certificate_arn`) com redirect HTTP -> HTTPS.
- Por quê:
  - Reduzir superfície de exposição e alinhar com boas práticas de segurança de borda/acesso.

3.5 Observabilidade (evolução aplicada)
- Feito:
  - Logs de control plane EKS e alarmes técnicos (CPU/memória/pods).
  - Alarmes de aplicação/negócio: latência, healthcheck success rate, falhas de processamento.
  - Dashboard com:
    - volume diário de ordens,
    - tempo médio por status (Diagnostico, Execucao, Finalizacao),
    - erros de integração,
    - latência e uptime.
- Por quê:
  - Cobrir requisitos do desafio com visibilidade técnica e de negócio.

3.6 CI/CD
- Feito:
  - Workflow de validação em PR.
  - Workflow de deploy automático em push para `homolog` e `prod`.
- Por quê:
  - Garantir qualidade mínima e automação de entrega em ambiente.
